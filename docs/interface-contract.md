# Контракт операции добавления расхода

## Связь с требованиями

- **Пользовательский сценарий:** [US-4 «Учёт расходов»](01-requirements.md#us-4-учёт-расходов-fr-4--ключевой-сценарий).
- **Функциональное требование:** [FR-4](01-requirements.md#1-функциональные-требования) — пользователь может добавлять, изменять, удалять и искать свои расходы по категории, году и месяцу.
- **Выбранная операция:** `POST /api/expenses` — добавление расхода текущего пользователя.
- **Статус:** операция реализована на backend и вызывается frontend-клиентом.

## Назначение

Операция выполняет шаг 2 сценария US-4: сохраняет расход с выбранной пользователем категорией и суммой. Месяц, год и владелец расхода не принимаются от клиента: backend определяет текущие месяц и год, а `user_uuid` получает из JWT. Это связывает запись с аутентифицированным пользователем.

## HTTP-контракт

**Метод и путь:** `POST /api/expenses`

**Вызывающая сторона:** страница расходов React-приложения вызывает метод `ItemService.addItem("/expenses", item)`. Эту же операцию можно вызвать любым HTTP-клиентом, отправив `POST` на `/api/expenses`.

**Авторизация:** заголовок `Authorization: Bearer <access-token>` обязателен. UUID пользователя берётся из поля `sub` access-токена.

**Тело запроса:** `application/json`.

| Поле | Тип | Ограничения | Назначение |
| --- | --- | --- | --- |
| `name` | `string` | длина от 1 до 32 символов | Название существующей категории текущего пользователя |
| `value` | `decimal` | значение не меньше `0` | Сумма расхода |

Оба поля обязательны. Для успешного вызова access-токен должен быть действительным, категория `name` должна принадлежать текущему пользователю, а расход с таким названием у пользователя должен отсутствовать. Месяц, год и `user_uuid` передавать не нужно: сервер определяет их самостоятельно.

### Результаты

| Код | Тело ответа | Условие |
| --- | --- | --- |
| `201 Created` | `null` | Расход сохранён |
| `401 Unauthorized` | стандартная ошибка FastAPI | Заголовок Bearer отсутствует |
| `403 Forbidden` | `{"detail":"The token has expired"}` или `{"detail":"Invalid token"}` | Access-токен просрочен или некорректен |
| `422 Unprocessable Entity` | `{"detail":"The category does not exist"}` | Категория с таким именем не найдена у текущего пользователя |
| `422 Unprocessable Entity` | `{"detail":"This expense already exist"}` | У пользователя уже есть расход с таким названием |
| `422 Unprocessable Entity` | описание ошибок валидации FastAPI | Нарушены ограничения полей `name` или `value` |

При успехе backend создаёт строку в `expenses` со значениями `name` и `value` из запроса, UUID текущего пользователя и текущими месяцем и годом, после чего фиксирует транзакцию.

## Примеры

### 1. Успешное добавление расхода

У пользователя с UUID `3f6c2a10-9b7d-4e8a-a1c4-5d2e7f901234` уже существует категория расходов `Бензин`, но расход с таким названием ещё не создан. Клиент отправляет действительный access-токен этого пользователя:

```http
POST /api/expenses HTTP/1.1
Authorization: Bearer <access-token>
Content-Type: application/json

{
  "name": "Бензин",
  "value": 3500.00
}
```

Ожидаемый HTTP-ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json

null
```

Ожидаемый результат: если серверная дата — ноябрь 2026 года, в `expenses` создаётся одна строка с `name="Бензин"`, `value=3500.00`, `month=11`, `year=2026` и `user_uuid="3f6c2a10-9b7d-4e8a-a1c4-5d2e7f901234"`.

### 2. Ошибка: категория не существует

У того же пользователя нет категории `Аренда самолёта`. Клиент отправляет:

```http
POST /api/expenses HTTP/1.1
Authorization: Bearer <access-token>
Content-Type: application/json

{
  "name": "Аренда самолёта",
  "value": 150000.00
}
```

Ожидаемый HTTP-ответ:

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "detail": "The category does not exist"
}
```

Вызывающая сторона распознаёт ошибку по коду `422` и значению поля `detail`. Новая строка в `expenses` не создаётся, транзакция не фиксируется.
